# 冗長になっても仕方ない処理まとめ

## 📌 概要

プログラミングでは「コードは簡潔に」が基本ですが、  
**冗長になっても仕方ない処理**も存在します。

これらは「分かりやすさ・保守性・安全性」を優先するため、  
あえて細かく分割して書くのが正解です。

---

## 🔥 冗長になっても仕方ない処理の代表例

### 1️⃣ **バリデーション（入力チェック）**

#### 特徴
- 入力項目ごとに細かくチェックが必要
- エラーメッセージも項目ごとに変える必要がある

#### 例
```javascript
nameError() {
  if (!this.userProfile.name) {
    return '名前を入力してください';
  }
  if (this.userProfile.name.length < 2) {
    return '名前は2文字以上で入力してください';
  }
  return '';
}

mobileError() {
  if (this.userProfile.mobile && Validate.hasHyphen(this.userProfile.mobile)) {
    return 'ハイフンは入力しないでください';
  }
  if (this.userProfile.mobile && !Validate.isValidMobileFirstNumber(this.userProfile.mobile)) {
    return '電話番号は0から始まる必要があります';
  }
  if (this.userProfile.mobile && !Validate.isValidMobile(this.userProfile.mobile)) {
    return '電話番号は10〜11桁の数字で入力してください';
  }
  return '';
}
```

#### なぜ冗長でもOKか
- **用途ごとに処理が違う**ため、分けないと保守できない
- **エラーメッセージを分ける**必要があるため、まとめられない
- **再利用性**が高くなる（他のページでも同じバリデーションを使える）

---

### 2️⃣ **エラーハンドリング**

#### 特徴
- エラーの種類ごとに対応が変わる
- ユーザーに適切なメッセージを表示する必要がある

#### 例
```javascript
async fetchData() {
  try {
    let res = await apiCall();
    return res;
  } catch (error) {
    if (error.response.status === 404) {
      alert('データが見つかりませんでした');
    } else if (error.response.status === 500) {
      alert('サーバーエラーが発生しました');
    } else if (error.response.status === 401) {
      alert('認証エラーです。ログインしてください');
    } else {
      alert('予期しないエラーが発生しました');
    }
    console.error(error);
  }
}
```

#### なぜ冗長でもOKか
- **エラーの種類ごとに対応が違う**
- **ユーザーに分かりやすいメッセージを出す**ため、細かく分岐が必要
- **安全性**を確保するため、例外処理を細かく書く必要がある

---

### 3️⃣ **権限・認可チェック**

#### 特徴
- ユーザーごとに操作可能な機能が違う
- 条件が複雑になりやすい

#### 例
```javascript
canEdit() {
  if (!this.userInfo) {
    return false; // 未ログイン
  }
  if (this.userInfo.role === 'admin') {
    return true; // 管理者は全て編集可能
  }
  if (this.userInfo.role === 'editor' && this.post.author_id === this.userInfo.user_id) {
    return true; // 編集者は自分の投稿のみ編集可能
  }
  return false; // それ以外は編集不可
}
```

#### なぜ冗長でもOKか
- **ユーザーの役割ごとに処理が違う**
- **セキュリティ上、細かく条件を書く必要がある**
- **分かりやすさ優先**で、条件を明確に書く

---

### 4️⃣ **入力フォームの状態管理**

#### 特徴
- 複数の入力項目ごとに状態を管理
- 項目ごとに違う処理が必要

#### 例
```javascript
computed: {
  isNameValid() {
    return Validate.isValidName(this.userProfile.name);
  },
  isMobileValid() {
    return Validate.isValidMobile(this.userProfile.mobile);
  },
  isEmailValid() {
    return Validate.email(this.userProfile.email);
  },
  isFormValid() {
    return this.isNameValid && this.isMobileValid && this.isEmailValid;
  }
}
```

#### なぜ冗長でもOKか
- **項目ごとに状態を管理**する必要があるため
- **再利用性**が高い（他の画面でも同じ状態管理を使える）
- **テンプレートで使いやすい**（`v-if="isNameValid"`のように使える）

---

### 5️⃣ **複雑なビジネスロジック**

#### 特徴
- 業務ルールや計算式が多岐にわたる
- 仕様ごとに分岐や例外処理が増える

#### 例
```javascript
calculateShippingFee(totalAmount, area, weight) {
  let fee = 0;
  
  // 地域別基本料金
  if (area === '北海道') {
    fee = 1000;
  } else if (area === '沖縄') {
    fee = 1500;
  } else {
    fee = 500;
  }
  
  // 重量による追加料金
  if (weight > 10) {
    fee += 500;
  } else if (weight > 5) {
    fee += 300;
  }
  
  // 合計金額による送料無料
  if (totalAmount >= 5000) {
    fee = 0;
  }
  
  return fee;
}
```

#### なぜ冗長でもOKか
- **業務ルールが複雑**で、条件分岐が多い
- **仕様変更に対応しやすい**ように、条件を明確に書く
- **可読性優先**で、処理の流れを分かりやすくする

---

## ✅ まとめ

### 冗長になっても仕方ない処理の共通点

1. **用途ごとに処理が違う**
2. **安全性・保守性を優先する必要がある**
3. **エラーメッセージや状態を細かく管理する必要がある**
4. **再利用性が高い**
5. **可読性・分かりやすさを優先する**

---

### プログラミングの鉄則

- **「簡潔さ」より「分かりやすさ・保守性」を優先する場合もある**
- **冗長でも、後から修正しやすいコードが良いコード**
- **実務では「動く」より「保守できる」コードが求められる**

---

## 🔥 重要なポイント

**「冗長＝悪」ではない！**

- バリデーション、エラーハンドリング、権限チェックなどは、  
  **冗長に見えても細かく分けるのが正解**です。

- 実務では「簡潔さ」より「保守性・安全性」を優先します。
