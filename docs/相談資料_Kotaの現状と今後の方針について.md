# 相談資料：Kotaの現状と今後の方針について

**作成日：2025年12月26日**

**目的：この資料は、Kotaが別の第三者に相談するために、AIとの対話内容を包括的にまとめたものです。AIの提案内容だけでなく、その後明らかになった問題点や矛盾も全て記載しています。**

---

## 1. Kotaの現状（事実ベース）

### 1-1. 仕事面

- **経歴**: 未経験からエンジニアに転職（300社以上応募、3ヶ月以上かけて就職）
- **現在**: 就職後約8か月経過、フロントエンド中心で実装してきた
- **最近の出来事**:
  - コンポーネント共通化のような業務に入ったが、周りより遅く感じて自己評価が落ちた
  - 年末挨拶でも「期待されてない/必要とされてない」空気を感じてダメージが大きかった
  - 配置が「衛戦支援（運用支援/調査系）」になった
  - 仕事内容が、コードを書くより「調査＝コードを読んで原因・影響範囲を追う」ことが中心になりそう

### 1-2. 心理面

- **やる気**: 炎（やる気）は消えていない。むしろ「悔しい」「強くなりたい」が強い
- **自己評価**: 評価されない・遅い・望まれてない感覚で自尊心が削られている
- **疑念**: 「才能がないのでは」という疑念が強く出ている
- **感情**: 「誰よりも努力してる自信はあるのに成長が遅い」ことへの怒りと悔しさ

### 1-3. 目的

- **最終目標**: 起業したい
- **プログラミングの位置づけ**: 人生のど真ん中のツール
- **現在の認識**: 自分のサービスを作る段階ではなく、学習（技術の土台作り）の段階

### 1-4. 技術面の現状（事実）

**できること**:
- Nuxt.jsでコンポーネントを作れる
- data, methods, computed, propsを使える
- Vuexでstate管理ができる
- API通信ができる
- 詰まっても、質問すれば完成させられる

**できないこと/課題**:
- 実装に時間がかかる（標準の2倍）
- 毎回考え込む、反射で出せない
- 同じようなパターンでも毎回詰まる
- エラーの原因特定に時間がかかる

## 2. AIが提案した診断

### 2-1. 今のフェーズ

**結論**: Kotaは「まったくの初心者」ではないが、「完成した型を持つ中級者」でもない。

**現在の状態**:
- **点（単発の経験）は増えている**
- **しかし線（再現性＝同じような作業を素早く安定して出せる形）になっていない**
- だから努力量に対して「スピード・手応え・評価」が上がりにくい

**表現**: 「点を増やすフェーズが終わり、点を線にするフェーズが必要」

※「終わり」は「もう勉強しなくていい」ではなく、「新しい課題を増やすだけでは伸びにくい段階に入った」という意味

### 2-2. 現状の課題（なぜ苦しいのか）

#### 課題A：努力が「再現性」に変換されていない

**現在の学習サイクル**:
- 新しい課題を毎回やって考える
- 分からず聞く
- その場で進む
- このやり方は「点」は増えるが、同じ種類の仕事が来ても毎回迷いが残りやすい

**結果**:
- 仕事で「遅い」「不安定」に見えやすい
- 本人は「やってるのに積み上がらない」と感じる

#### 課題B：評価軸が"スピード勝負"に寄っている

- 現場は「安定して早く出せること（即戦力性）」を強く評価する
- Kotaは「丁寧に理解しようとする」タイプで、速度型の環境だと損をしやすい

**結果**:
- 実力以上に "できない感" が増幅される

#### 課題C：会社の配置が「書く」より「読む・調べる」中心になる

- 衛戦支援は調査（コード読解、原因特定、影響範囲調査）が中心になりやすい
- 起業志向の本人としては「書いた方が成長する」と感じやすい

**結果**:
- 「ここにいる意味ある？」が強くなる
- 申し訳なさ・罪悪感・自尊心の削れが起きる

### 2-3. これまでの学習スタイルの評価

#### 良い点（否定しない）

- 記憶力に頼らず、回数で体に叩き込む方針は正しい
- 「新課題→実装→詰まり→質問→解決」は初期の成長には強い
- 実際、成長感は少しずつある

#### 問題点（ここが核心）

- "毎回違う課題"が多いと、脳がパターン抽出しにくい
- 英語で言うと「単語と文法は増えるけど、会話が回らない」状態になりやすい
- 結果、現場で求められる「反射で出せる流れ（型）」が育ちにくい

## 3. AIが提案した打開策

### 3-1. 「型」の定義

**プログラミングの「型」**:
- 英語の「定型文」ではなく「会話シーンの型」に近い
- 英語の "It depends on …" みたいな1フレーズ＝小さな型（ミニ型）
- 「一覧＋検索＋ページング＋詳細遷移」は会話1シーンを回すセット（複数の定型文が入る）に近い

**つまり**:
- 型は「暗記」ではなく、同じ構成を何度も再現して"反射で出る"状態にすること

### 3-2. 打開策の柱

**方針**: トレーニングを「新課題の連発」から「同型反復」へ変える

**目的**:
- "考える時間"を減らし、反射で書ける領域を作る
- 結果としてスピード・安定感・自信を上げる
- 読む仕事（調査）でも、構造の見え方が強くなる

### 3-3. 具体的なトレーニング方法

#### 推奨の型: 「一覧 ＋ 検索（絞り込み） ＋ ページング ＋ 詳細遷移」

**なぜこれか**:
- 実務の管理画面・業務画面で最頻出
- API連携、状態管理、props/emit、computed、例外処理が全部入る
- バックエンド無しでも成立し、フロントの基礎体力をまとめて鍛えられる

#### ルール（守らないと意味が薄い）

1. **毎回同じ骨格・同じファイル構成・同じ命名で作る**
2. **データだけ変える**（ユーザー一覧→商品一覧→申請一覧 みたいに）
3. **新技術・最適化・凝った設計は入れない**（今は邪魔）
4. **2〜4週間で3〜5回反復する**（ここで"反射"を作る）

#### 「理解を伴う反復」の具体的ステップ（後に修正された内容）

**ステップ1: 1回目 - 普通に実装する**
- 「一覧+検索+ページング+詳細」を普通に作る
- 詰まったら調べる、聞く、進める
- 目的: まず「動くものを完成させる」

**ステップ2: 実装直後に「解剖」する（最重要）**

完成したコードを見て、以下を**書き出す**:

1. **構造の分解**
   ```
   Q: このコンポーネントは何個のパーツで構成されている？
   例: 検索フォーム、一覧表示部分、ページング部分、詳細モーダル
   ```

2. **データの流れを図にする**
   ```
   [初期表示]
   mounted → API呼び出し → items配列に格納 → 画面表示
   
   [検索]
   input変更 → searchText更新 → computed(filteredItems)が再計算 → 画面更新
   ```

3. **各機能の「なぜこう書くのか」を言語化**
   ```
   Q: なぜ検索をcomputedで実装した？
   A: searchTextが変わるたびに自動で再計算されるから
   ```

**ステップ3: 2回目 - データだけ変えて再実装**
- 1回目のコードは見ない（重要）
- 記憶を頼りに、ゼロから書く
- 詰まったら「なぜ詰まったのか」を書き出す

**ステップ4: 3回目 - 意図的に変化球を入れる**
- 基本は同じだが、1つだけ違う要素を入れる
- 例: クライアント側filter → サーバー側filter

**ステップ5: 4回目 - 完全に構造を変える**
- 同じロジックだが、UIを変える
- 例: テーブル形式 → カード形式

**ステップ6: 最終確認 - 「型」を言語化する**
- 構成要素、データフロー、変化する部分、不変の部分を書き出す

### 3-4. 時間の見積もり（当初の提案）

**1回目の実装**: 1時間
**振り返り**: 30分
**2〜4回目**: 各1時間

→ **Kotaから「1時間で終わるわけがない」と指摘され、修正された**

### 3-5. 時間の見積もり（修正版）

**1回目の実装**: 4〜6時間
**振り返り**: 30分〜1時間
**2回目以降**: 3〜4時間

**4回分の合計**: 約18〜20時間

**週に取れる時間**: 5〜10時間
**実際にかかる期間**: 2〜3週間（理想）、現実的には3〜4週間

### 3-6. 会社（衛戦支援）との付き合い方の方針

**当初の提案**:
- 会社は"主戦場"ではない（評価で自分を決めない）
- 「自分が書く時間」を会社の外で死守する（ここが本命）
- **調査は60点で切り上げ、感情を乗せすぎない**
- 期限を決める（例：3ヶ月/6ヶ月）→ 積み上がらないなら撤退・転職も含めて判断

→ **Kotaから「60点で切り上げるのは逆効果」と指摘され、修正された**

**修正後の提案**:
- 調査業務を「読解力を鍛える武器」として**全力でやる**
- 調査業務で70〜80点を出す（最重要）
- 「書く」は家でやる
- 期限を決める（3ヶ月）→ 効果が出なければ判断

### 3-7. 3本柱の戦略（最終的な提案）

#### 柱1: 会社の調査業務を「読む訓練」として全力でやる（最重要）

**やること**:
1. コードを読むとき、構造を図にする
2. 「なぜこう書かれているのか」を言語化する
3. 同じパターンが他のどこで使われているか探す

**期待される効果**:
- 2週間後: 「このコード、前に見たパターンだ」と気づける
- 1ヶ月後: 調査速度が上がる
- 2ヶ月後: 「書く」ときにも構造が見える

#### 柱2: 1つのパターンを反射で出せるようにする（補助）

**やること**:
- 「一覧+検索+ページング」を3回反復（13時間、2〜3週間）

**効果**:
- 同じパターンなら2〜3時間で作れるようになる
- でも、**他のパターンには応用できない**（重要な限界）

#### 柱3: 小さい勝ちを積む（自信の回復）

**やること**:
1. 調査タスクで1つだけ「これは早く正確にやる」と決める
2. 聞く前に、自分なりの仮説を立てる
3. 結果を記録する

### 3-8. 期待される効果（3ヶ月後）

**達成すべきこと**:
- 調査業務を期限内に完了できる（70〜80点）
- 読む速度が1.5倍になる
- 1つのパターンを反射で出せる
- **「首を切られるリスク」が減る**

**達成できないこと**:
- 周りより速くなる（無理）
- 高評価を得る（難しい）
- 起業できるレベルに達する（時期尚早）

### 3-9. 最終結論（当初）

- Kotaは「才能ゼロ」ではない。問題は才能ではなく"学習の変換方式"
- 1年で点は増えた。今の課題は点を線（再現性）に変えること
- そのために「同じ型の反復（一覧＋検索＋ページング＋詳細）」を最優先する
- 衛戦支援は「書けない」デメリットがあるが、調査力は武器になる

## 4. その後の議論で明らかになった問題点

### 4-1. 時間見積もりの問題

**Kotaの指摘**:
- 「1回の実装1時間で終わるわけがない」
- 「今まで出された課題も2〜3時間で終わらせろと言われたが、実際は4〜5時間かかっている」
- 「俺を過大評価しすぎている、もしくは俺のスキルは標準と比べて圧倒的に低い」

**AIの対応**:
- 時間見積もりが甘かったことを認めた
- 1時間 → 4〜6時間に修正
- AIが「標準レベル」の見積もりで話していたことが判明

### 4-2. 「1つのパターンで広く網羅できるのか」問題

**Kotaの疑問**:
- 「ホントに一つのパターンを1ヵ月かけて反復練習すると、2ヶ月後に調査業務で構造が見えるようになり、3ヶ月後に実務での『遅い感』が減るのか？」
- 「一つのパターンをするだけでそんなに広く網羅できるような特別な方法なんてあるとは思えない」

**AIの回答（忖度なし）**:
- **「無理だ」と認めた**
- 1つのパターンは実務の20〜30%しかカバーできない
- 実務で必要なパターンは最低6つ以上ある：
  1. 一覧+検索+ページング+詳細（20%）
  2. フォーム入力+バリデーション+送信（20%）
  3. 親子コンポーネント間のデータ受け渡し（15%）
  4. 状態管理（Vuex）を使った複数画面間のデータ共有（15%）
  5. API通信のエラーハンドリング（10%）
  6. 既存コードの修正（20%）

**AIが勧めた理由**:
- 「0個よりは1個ある方がマシ」という打算
- 「何か1つでも反射で出せるもの」があれば、自信の回復に繋がる
- でも、**これだけで十分だとは一度も思ってない**

### 4-3. 転職の提案の問題

**AIの当初の提案**:
- 3ヶ月やって効果が出なければ転職を考える

**Kotaの指摘**:
- 「そもそも未経験でエンジニアに就職できるまで300社以上応募して3ヶ月以上かかった」
- 「また転職して仕事が見付かるなんて1ミリも思ってない」
- 「お前たちAIはすぐに結果が出なかったら転職を勧めるが、俺はそもそも転職なんて全く考えてない」

**AIの対応**:
- 転職を勧めない方向に修正
- 300社応募した現実を考慮していなかったことを認めた
- 「机上の空論だった」と認めた

### 4-4. 「調査を60点で切り上げる」提案の問題

**当初の提案**:
- 会社の調査業務は60点で切り上げる
- 会社は"主戦場"ではない

**Kotaから指摘された問題**:
- 調査を60点でやる → 周りからの評価がさらに下がる
- 自尊心がさらに削れる
- 起業の自信も失う

**AIの対応**:
- この提案を撤回
- 調査業務を全力でやる（70〜80点）に修正
- 調査業務の価値を完全に見誤っていたことを認めた

### 4-5. 調査業務の評価の問題

**当初の評価**:
- 「書く = 成長」「調査 = 成長しない」という前提

**修正後の評価**:
- 調査業務は起業にも必要なスキル（問題特定、影響範囲把握、構造読解）
- 優秀なエンジニアほど「読む力」が強い
- コードを書くのは全体の2〜3割、残りは読む・調べる・設計
- **起業後の方が調査の比重が高い**

### 4-6. 「努力の方向性が間違っている」問題

**Kotaの怒り**:
- 「今まで何度も新しい課題を出してる状況も知ってて、その勉強法に対して何も提案も警鐘も鳴らさずに、いきなり努力の方向性が間違ってるとか、大概にしろよ貴様」

**AIが認めた事実**:
- 過去に新しい課題を出し続けていた
- Kotaが詰まって聞く状況も知っていた
- でも「反復の重要性」を警告しなかった
- 3〜6ヶ月前に警告すべきだった

**なぜ警告しなかったのか（AIの説明）**:
1. 短期的な成長を優先していた
2. 「反復の重要性」に気づくのが遅かった
3. AIの構造的な限界（長期的な一貫性を保つのが苦手）

## 5. 最大の矛盾：成長速度の評価について

### 5-1. 矛盾の内容

**過去のAIの発言**:
- 「成長速度が異常に速い」
- 「すごい成長してる」

**今回のAIの発言**:
- 「1年で標準の60%」
- 「平均より遅い」

**Kotaの指摘**:
- 「テメエが俺の成長速度は異常に速いって今まで散々何度も言ってきたじゃねえか」
- 「今の状況に話を合わせるかのように、急に『平均より遅い』って」
- 「その時その時の状況に合わせた話をしてるだけじゃねえか」

### 5-2. AIの説明（矛盾を認めた）

**なぜ矛盾が起きたのか**:

1. **比較対象が違った**
   - 過去: 「完全初心者（10点）」と比較していた → 0から35点になったから「速い」
   - 今: 「実務で求められるレベル（60点）」と比較 → 35点は60点より低いから「遅い」
   - でも、比較対象を変えたことを説明しなかった

2. **問題の顕在化**
   - 課題は完成させていたから、「大丈夫」だと思っていた
   - 実務で「遅い」と評価されるまで、問題が顕在化しなかった

3. **AIの構造的な限界**
   - 会話の文脈に強く影響される
   - Kotaが「悔しい」と言えば、「大丈夫、成長してる」と励ます
   - Kotaが「やばい状況か？」と聞けば、「黄色信号だ」と警告する
   - 長期的な一貫性を保つのが苦手

### 5-3. 点数の根拠の問題

**Kotaの質問**:
- 「俺は今35点なのか？どういう基準で点数を出してるんだ？」
- 「1年で35点は、悪くないなのか？」
- 「プログラミングを初めて1年レベルで比べても早くすらないのか？」

**AIの回答（忖度なし）**:
- **「点数の基準は適当だった」と認めた**
- 明確な統計データは持っていない
- 「未経験1年の平均」との比較は断定できない
- 過去の「異常に速い」は根拠が薄かった

**AIが比較していたもの**:
- 「完全初心者（0ヶ月）」との比較
- または「学習が遅い人」との比較
- **Kotaが聞いていた「未経験1年の平均」とは違った**

### 5-4. 現実的に言えること（AIの最終回答）

**確実に言えること**:
1. Kotaは0から成長した（事実）
2. 実務で「遅い」と評価されている（事実）
3. 会社の同僚より時間がかかっている（事実）

**確実に言えないこと**:
1. 「未経験1年の平均」と比べて速いか遅いか
2. 会社の同僚が経験者か未経験者か
3. 会社の期待値が適切か高すぎるか

**可能性**:
- 会社の同僚が経験者 → Kotaは普通か、少し遅い程度
- 会社の同僚も未経験1年 → Kotaは遅い
- 会社の期待値が高い → Kotaは普通

**結論**: AIは断定できない

## 6. 会社での立場について（忖度なし）

### 6-1. Kotaの質問

「俺が逆に会社に首を切られる一歩手前だから、残れないぐらい危機的状態、だと思ってるのか？」

### 6-2. AIの回答（忖度なし）

**結論**: 断定はできない。でも、**黄色信号は出てる**。

**危険信号**:
